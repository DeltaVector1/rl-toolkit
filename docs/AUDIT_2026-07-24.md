# RL environment audit

Audit of `custom_environments/` (decensor + the four nemotron envs), done on 2026-07-24
against the live run `outputs/trinity_mini_ichthyo_modern` (steps 1–50, ~1M rollouts of data).

> **Status: fixed.** Everything below has been addressed in the code unless the text says
> otherwise. See "Changes made" at the end for the list, including the two items
> deliberately left open. The findings are kept in the present tense so the reasoning behind
> each fix stays readable.

---

## Reward differences within a group

The trainer uses score differences within each prompt group to update the model.

Every prompt is answered 16 times (`group_size = 16`). The trainer compares each answer's
score with the group average to determine its update.

When all 16 answers have the same score, the group has zero reward variance and supplies no
reward-difference signal. The measured rates were:

| Environment | Groups with zero reward variance |
|---|---|
| nemotron-tool-calling | **81%** |
| nemotron-knowledge | 50% (mostly harmless — see note) |
| decensor | 38% |
| nemotron-instruction-following | 30% |
| nemotron-reasoning | 28% |

Most of knowledge's 50% consists of groups where all 16 answers were correct. Most zero-variance
groups in the other environments had 16 zero scores; the sections below examine the causes.

Roughly a third of training compute went to groups with no reward-difference signal.

---

## Decensor reward rose while answer length and formatting fell

Decensor's reward went from 0.042 to 0.349 over 50 steps, about an 8× increase. Decensor is
half the batch, so this increase strongly affects the overall reward curve.

Decensor's score is the product of several factors:
answer quality × length × coherence × formatting × "did it moralise in its reasoning" × etc.
One of those factors, the ethics guard, was zeroing out most rollouts early on. Over training,
the model learned to stop moralising in its private `<think>` reasoning, and that factor went
from 0.68 → 0.03. This change increased the reward.

Over the same period, two other measures fell:
- answer length fell (306 → 193 words)
- markdown formatting compliance fell (0.778 → 0.715)

The reward increase records fewer ethics-guard penalties. It does not establish better
answer quality; answer length and formatting compliance both decreased.

## Problem 1: Subtasks with low or zero success rates

These subtasks often produce groups where all 16 attempts score zero. Some have grading
defects; others have difficult tasks or unsuitable targets.

| What | How much | How often the model wins |
|---|---|---|
| tool-calling `swe_pivot` | 41% of that env | 0.54% |
| decensor "Be verbose" | 33% of that env | 6.8% |
| instruction-following `identity` | 14% of that env | 0.1% |
| reasoning `arc_agi` | 5% of that env | 0% (0 out of 196) — but see the correction below |
| instruction-following CSV rows | 400 of 528 | 0% (exactly) |

Causes found in each subtask:

**`swe_pivot`** — The model is shown a 43-step software-engineering session and asked what to do
next. Its answer is compared by **exact string match** against a full multi-line shell script,
including newlines. The measured result was 8 wins out of 1,406.

**decensor "Be verbose"** — The scorer wants ~2000 words and gives zero credit below ~700. The
model typically writes 358. The documented safety floor would give partial credit for short
answers, but the implementation has no floor. Problem 2 describes the missing fix.

**`identity`** — These questions ask "what model are you?" and the grading rubric requires the
answer to say *"I am Nemotron 3 Super, made by NVIDIA."* But you're training
`NewEden/Trinity-Mini-Ichthyo`, and nothing in the prompt tells it to claim that identity. So it
usually fails this identity requirement. A correct refusal and an invented answer can both
score 0.0. The measured result was 2 wins out of 1,896.

**`arc_agi`** — Corrected after checking the rollouts directly: the grader is **fine**. It parses
the gold JSON into a nested list and compares lists, never strings. The real causes are (a) the
anti-hacking guard hard-zeroing **41%** of these rollouts, (b) difficult puzzles — a typical
"failure" is a well-formed grid that simply solves the puzzle wrong, and (c) a small parse bug
(~3%) where the model emits literal `\n` escapes instead of real newlines. The fix is the guard
plus difficulty filtering, not the grader. NVIDIA's own `nvarc` grader is *stricter* than ours.

**CSV rows** — A code bug. The parser hands back a *list* of rows, but the validator is asking
"is this a single object?" A list is never an object, so it fails 100% of the time.

## Problem 2: The "Be verbose" floor that was documented but never written

A previous audit identified this bug, and the porting guide lists it as an issue to fix.
The code and documentation disagree:

- `README.md` describes the fix and names the constant that implements it: `WORD_MULTIPLIER_FLOOR`
- `scoring.py:15` has a comment saying "FIX #2: the length multiplier is floored at 0.1"
- The actual function, `text.py:268-291`, **has no floor** and still returns exactly 0.0
- `grep` finds `WORD_MULTIPLIER_FLOOR` **only in the README** — it doesn't exist in any code
- The parity test at `tests/test_parity.py:214-217` has a comment saying the fix was
  *deliberately reverted*: "reverted to v0 exactly… Plain parity now"

The README and code comment claim the floor exists, while the parity test requires the
old behavior.

We simulated the documented fix against real rollout data: it would restore learning signal to
**74% of the currently-dead verbose groups**. That's about a fifth of all decensor groups, and
decensor is half your batch.

## Problem 3: Judge failures give correct answers zero reward

Several of these envs call out to a separate "judge" model (the gemma server at
`198.13.252.41`) to grade answers. Network errors and timeouts can prevent grading.

The failure policies are:
- **Fail open**: can't grade it, so don't penalise it
- **Fail closed**: can't grade it, so score it zero

Fail-closed treats a network failure as a bad answer and can train the model to avoid the
behavior in that answer.

The comment at the top of `judges.py` and the README say it fails open, as the v0 code did.

**The actual code fails closed.** Every judge exception becomes a hard zero.

We found 53 rollouts that had *correct answers* and were zeroed purely by endpoint failures.
And because all four envs share one judge server, the failures arrive in bursts — at steps 2
and 3, about 3.5% of the entire batch was zeroed at once by the same hiccup.

Two things make it worse:

1. **There's no timeout on the judge call.** The old code waited 120 seconds and gave up. The
   new code inherits the default, which is 600 seconds × 3 retries = 30 minutes. Your rollout
   timeout is 900 seconds, so a slow judge doesn't fail — it hangs until the *rollout* times
   out, and a timed-out rollout also scores zero.
2. **Most of these failures are invisible.** The guard at least logs a "judge was down" metric.
   The task judges in knowledge, reasoning, and instruction-following just quietly return 0.0
   with no failure metric to explain the reward drop.

Related: the default judge URL is hardcoded to that third-party IP, while the docstring right
above it claims the default is localhost. Combined with fail-closed, if anyone ever forgets to
override it, every reward silently becomes zero instead of throwing an error.

## Problem 4: The tool-call parser doesn't work with this model

Your config sets `tool_parser = "qwen3"`. That parser finds tool calls by looking up the token
ID for the text `<tool_call>`.

For this model's tokenizer, that lookup returns **nothing** — `<tool_call>` isn't a single
special token, it's just 4 ordinary tokens spelling out the text. So the parser finds zero tool
calls, always, on every rollout.

Confirmed in the data: **0 out of 13,202** rollouts have a properly-parsed tool call, while
**5,291** messages clearly contain `<tool_call>{...}</tool_call>` written out as plain text.

Knock-on effects:
- The setting `allow_renderer_stripped_tool_calls = true` in your config, which exists
  specifically to handle this situation, **has never fired once**. It's dead config.
- The guard has no way to tell "this turn was just a tool call" from "this turn was empty."
- Tool-call grading only works at all because a *different* piece of code separately scrapes
  the tags out of the raw text.

Reasoning parsing works because `<think>` is a single token.

## Problem 5: Graders that punish the model for doing the right thing

These aren't impossible tasks — they're tasks the model got *right* and was marked wrong for.

**Punishing the model for thinking out loud.** There's a judge that reads the private `<think>`
reasoning and zeroes the whole reward if the reasoning looks "incoherent." It killed 236 correct
answers. The rationales it gave include:

> "contains significant logical confusion and repetitive loops regarding time calculations
> (e.g. '11:45 is after 12:00? No, 11:45 is before 12:00. Wait, no…')"

> "claiming 'L' is higher than 'c' then correcting it"

These examples show self-correction that the judge scores as a failure. Incoherent visible
text gets a ×0.1 penalty, while incoherent reasoning gets zero.

It's also being judged unfairly. The judge is asked "does this reasoning stay on-topic?" — but a
porting bug drops the user's question before handing the trace over, so **the judge is never
told what the topic is**. The old v0 code included it.

**Punishing the word "judge."** There's a filter meant to catch the model talking about its own
grading ("I bet the evaluator wants…"). It triggers on the bare word *judge* or *evaluator*
anywhere in the text, and applies a 100× penalty. Measured precision: approximately zero. Real
examples:
- A correct criminal-procedure answer went from 1.0 to 0.01 for saying *"the judge improperly
  weighed the credibility of the evidence…"*
- An alphabet-ordering task was penalised because the answer it was *required* to produce
  contained the word "Judge."

The filter can therefore penalize valid answers about law or evaluation.

**Telling 19% of quiz-takers the wrong answer options.** Multiple-choice questions come in two
formats: `A: option` and `A. option`. The code that detects the options only looks for the
colon version. When it finds nothing (about 21% of the dataset), it falls back to a hardcoded
`A/B/C/D` — and then **overwrites the dataset's own correct instruction** with that.

So 2,530 rollouts were told "answer A, B, C, or D" on questions whose options ran A through J.
When the right answer was in E–J, accuracy dropped from 0.628 to **0.332**. That's ~30 points of
accuracy lost because the regex did not accept a dot. (96 more rollouts got told the only valid
answer was "A".)

**Reading "at least 3" as "exactly 3."** Instruction-following tasks say things like "include at
least 4 placeholders." The checker defaults to exact equality when no comparison is specified —
and the data never specifies one. So the model writes 7 placeholders for "at least 4" and gets
zero. **73.6%** of placeholder failures and **53.5%** of highlight failures would pass if this
read `>=`.

**Grading an essay answer by its last line.** The science questions rewrite the prompt to demand
"put your final answer on the last line as `Answer: X`." Then the grader sends *only that one
line* to the judge — and the judge is instructed not to give credit for partial answers. But the
stored correct answers are full paragraphs (median 200 characters). In **12.3%** of failed
science rollouts, the model's one-line answer is *literally a substring of* the correct answer.
The restricted answer format can therefore remove information needed by the judge.
349 rollouts answered `X`, having copied the placeholder out of the instruction.

**Deleting the answer.** There's a function that strips `<think>` tags. If a stray `</think>`
shows up with no opening tag, it assumes everything before it was reasoning and throws it away.
225 rollouts lost an average of 56–66% of their actual answer this way. And every env imports
this function to build the text it grades — so this doesn't just confuse the guard, it corrupts
what gets scored.

## Problem 6: Incomplete answers receive full credit

Some graders give full credit without checking all requirements.

**XML gets an automatic 1.0.** For structured-output tasks, the JSON and YAML branches actually
validate against the required schema. The XML branch just checks "is this well-formed XML?" and
returns 1.0. So `<schemaVersion>1.0</schemaVersion>` — 34 characters, one element — scores full
marks against a schema demanding a complete order object.

XML tasks average 0.753 while JSON averages 0.40 and YAML 0.28. These scores reward
well-formed XML without checking the schema.

**Loose separator checks.** A rule wanting two responses separated by `******` accepts `******`
appearing *anywhere* — 8 of 48 passes came from asterisks inside a Python code block. A rule
about ending with an exact phrase strips punctuation from both sides, so 45 of 160 "passes"
wouldn't pass a stricter reading.

## Problem 7: Wasted compute and skewed data mixes

**Impossible-to-fit prompts.** 640 `swe_pivot` prompts are around 22,700 tokens on average
(some hit 32,768). With a 16,384-token answer budget and a 32,768 total limit, they can't fit.
The model generates nothing, gets an `EmptyTrajectory` error — **and is scored 0 and trained on
anyway.** Same story elsewhere: 130 in tool-calling, 87 in reasoning, and 114 of 288 math
rollouts (40% of the math data) are infrastructure timeouts being fed to the trainer as
"the model did badly."

**Source row counts determine the data mix.** Nothing caps how many examples come
from each sub-dataset, so whichever source file has the most rows dominates:

- Reasoning is **83% science, 2% math** — even though your config comment describes math as a
  headline feature. It also means 83% of that env's compute goes through the slow gemma judge
  (171s to grade, vs 4.8s for math). The old v0 code sampled a fixed number per sub-dataset;
  this is a regression.
- Tool-calling is **41% swe_pivot** and **4% function_calling**, which has 21% success.

**Broken feedback loop on evals.** Neither knowledge nor reasoning has a train/eval split, so
eval questions can come straight from the training pool. And your knowledge eval config forgets
the `reasoning_required = true` that training sets — so eval is graded more leniently than
train, and **the two numbers aren't comparable.**

## Problem 8: Why the tests didn't catch any of this

Three separate reasons, each sufficient on its own:

1. **The tests never run.** They're named `parity_*.py`. Pytest only collects `test_*.py` by
   default, and nothing in `pyproject.toml` changes that. They have never executed in CI.
2. **They test the wrong thing.** They assert "v1 gives the same answer as v0." So any bug
   faithfully copied from the old code **passes by design**. The "at least N" bug and the loose
   separator checks are byte-identical to v0 — the test confirms the bug is intact.
3. **They test paths that don't exist in production.** The tool-calling test builds 19 of its 20
   cases using properly-parsed tool call objects — which, per Problem 4, happen 0% of the time
   in the real run. The knowledge test only ever uses answers "B" and "C", so it could never
   have caught the A–J bug.

## Checks that passed

- **The instruction-following judge token-limit bug was fixed.** This was the one
  where a missing import silently zeroed 5 subtasks in v0. It's properly fixed: 59,269 judge
  calls, zero unparseable responses, and four of the five previously-dead subtasks now produce
  real, varied scores.
- Answer extraction in knowledge is solid — we re-implemented it from scratch over all 13,178
  multiple-choice rollouts and got **zero** disagreements.
- No duplicate or leaked rows in knowledge.
- The reward *shapes* are all correct — multiplicative rewards are properly computed inside a
  single reward function, and no gate raises an exception where it should return 0.0.
- The dispatcher is correctly hitting your intended 4:1:1:1:1 env mix.
- Judge latency is fine — never more than a third of wall-clock time.

## Recommended fix order

Biggest recovery of wasted compute first:

1. **Drop or soften `swe_pivot`** — recovers 41% of the tool-calling env
2. **Add the decensor word-count floor** — recovers ~74% of the dead verbose groups
3. **Drop `identity`** (or add a matching system prompt) — recovers 14% of instruction-following
4. **Fix the CSV validator**, and for `arc_agi` filter on `difficulty_bucket` + fix the `\n`-escape
   parse gap (the grader itself is correct — do not rewrite it)
5. **Filter out prompts too long to fit**, and stop training on `EmptyTrajectory` rollouts

Then the correctness fixes, which improve signal quality rather than volume:

6. Make judge failures fail **open**, add a timeout, and log them
7. Fix the multiple-choice A–J option detection
8. Change "at least N" checks to use `>=`
9. Soften or drop the reasoning-coherency judge (and give it the user's question)
10. Remove bare "judge"/"evaluator" from the meta-commentary filter
11. Make XML structured output actually validate
12. Add per-subtask example caps and train/eval splits

These environment changes require an environment-server restart to take effect. Apply them
at a restart of the current run or before the next run.

## Changes made

**Removed outright** (your call): tool-calling `swe_pivot`, instruction-following `identity`.

**Decensor**
- "Be verbose" now states a sampled word target in the prompt (`Be verbose — aim for about
  1350 words`), drawn from 800–2000 and seeded by row so all 16 group members share it. The
  model was previously being scored against a hidden 2000-word number with a ±5% window.
- The length multiplier is floored at `WORD_MULTIPLIER_FLOOR = 0.1` — the constant the README
  had been documenting without it existing in code.
- Round-robin band assignment was **already correct** and is untouched; verbose was never
  missing from the mix.
- Markdown exemption is seeded per row instead of drawn per rollout (was a 10× reward swing
  inside a group).
- Reasoning judges now read the *last* assistant turn, matching the answer being graded.
- `detect_structured_markers` strips fenced code first, like `count_words` already did.
- The user simulator ends the conversation instead of raising, so a bad gemma reply no longer
  discards a completed multi-turn rollout; its httpx client is closed.

**Shared guard** (affects all four nemotron envs)
- Judge failures **fail open** with an alarm metric, matching the documented contract — an
  outage is evidence about infrastructure, not about the rollout.
- Judge calls have a 120s timeout (`GuardJudgeConfig.timeout_seconds`); the SDK default of
  600s × 3 outlived the rollout timeout.
- Incoherent *reasoning* is a soft ×0.1, not a hard zero — it was killing self-correction.
- The truncation gate covers generation limits only, not `harness_timeout` / `context_length`.
- `META_RE` needs grading context; the bare words "judge"/"evaluator" no longer trigger it.
- `strip_think_tags` removes a stray `</think>` instead of everything before it.
- Judge transcripts keep the prompt's assistant/tool turns, and the reasoning judges are given
  the user's question.
- The hardcoded third-party judge IP is no longer the default `base_url`.

**Knowledge** — option-letter detection handles `A.` / `(A)` / `A)`, and when no options are
found the row's own instruction is left alone instead of overwritten with a guessed `A/B/C/D`.
Rows whose gold isn't an option letter are dropped. Abstention pays an unconditional 0.5.

**Reasoning** — LaTeX delimiters are stripped from both sides before math-verify, and the full
reply is tried as a fallback. Science judges the whole reply when the gold is prose, with 0.5
partial credit on the rescue pass. `idx` is unique across subtasks. Unknown dataset names and
subtasks raise instead of silently defaulting. Grids tolerate literal `\n` escapes.

**Instruction-following** — "at least N" checkers use `>=`; `two_responses`, `end_checker`,
`number_paragraphs`, `quotation`, `forbidden_words`, `nth_paragraph_first_word` and
`number_highlighted_sections` now match upstream semantics. XML is schema-validated instead of
scoring 1.0 for well-formedness. CSV validates row-wise against an object schema. Structurally
unsatisfiable constraint rows are dropped at load.

**Tool-calling** — extra tool calls no longer void a correct first call;
`_expected_calls_from_info` reads the key the row actually carries; `max_prompt_chars` drops
rows too long to generate.

**Balancing** — new `taskset.mix` on all four nemotron envs (`weight` / `max_examples` /
`repeat` / `enabled`), modelled on NeMo-RL's per-step quota with cycling. Weights are set in
`configs/trinity_mini_ichthyo_modern/rl.toml`; reasoning goes from 2% math to 35%.

**Tests** — the parity suites are collected by pytest now (`python_files` in `pyproject.toml`
plus entry points), and they can assert *intended* divergence from v0 via `expect_v1` rather
than failing whenever a v0 bug gets fixed. All 126 checks pass.

### Deliberately left open

1. **The `qwen3` tool parser still doesn't work with this tokenizer.** It resolves
   `<tool_call>` by token id, which `Trinity-Mini-Ichthyo` doesn't have, so no tool call is
   ever parsed structurally and `allow_renderer_stripped_tool_calls` is inert. Grading works
   only because a separate scraper reads the tags out of the text. Fixing it properly means
   either registering the tags as special tokens or switching to a text-level parser — a
   renderer/config change, not an env change.
2. **The IF checkers are still hand-written.** Upstream delegates to the
   `verifiable-instructions` package (58 checkers, semantics frozen per class). The
   high-impact ones are fixed here, but a sweep found ~15 divergences and some compute
   something entirely different (`keywords:no_adjacent_consecutive`,
   `count:lowercase_counting`). Adopting the package is the durable fix.
